## 1. Part 4a: how Jev keeps its settings outside its plugin (verified)

- Jev is an installed agy plugin (`agy plugin list`: enabled, 2.3.20, 2 skills, 1 rule, 1 hook, 0 MCP servers), staged in `~/.gemini/config/plugins/jev/` and recorded in agy's import manifest.
- One plugin folder serves both harnesses: root `plugin.json` and `.claude-plugin/plugin.json`, `hooks.json` at the root for agy and `claude/hooks.json` for Claude Code, shared code under `src/core/`. agy ignores the `hooks` field of `plugin.json` and reads `<plugin-root>/hooks.json`; `agy plugin validate` warns about the unknown field.
- Jev's MCP server is **not** in the plugin for agy: the plugin's `.mcp.json` is "never loaded: this is Claude Code's file name", and the server is declared in the global `~/.gemini/config/mcp_config.json` (a stdio `command` and `args` with absolute paths, plus an `env` object that holds Jev's own API key under a key name). Claude Code's entry uses `${CLAUDE_PLUGIN_ROOT}` (agy does not expand it).
- Settings and secrets live outside the plugin: `~/.config/jev/` (`config.json`, an `env` file, session state), resolved in code from `JEV_CONFIG_FILE` or `~/.config/jev`, by the same core for both harnesses. The plugin folder is "replaced when the plugin updates", the files outside it are not touched.
- agy's docs: `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` are expanded in plugin MCP `args`, `cwd` and `env`; **OS environment variables are not expanded** in plugin MCP configs. A `${X}` is substituted only when `X` is declared in that server's `variables` and the user has filled it in on the plugin's setup form in `/plugin`; anything else is passed through literally (the validator says "isn't declared in variables, so it's passed as is"). A variable may be used in `url` and `headers`. A plugin that declares variables stays disabled after `agy plugin install` until they are filled in. **Unverified:** where agy stores the value, whether it survives an update, whether it can be pre-filled without the UI (no non-UI route is documented).

## 2. Part 5: a literal header on a global-scope server (verified)

What ran: agy (under the user's supervision, with backup, no printing of values, and the file's mode kept) added one server, `a2a-hdr-probe`, to the real `~/.gemini/config/mcp_config.json`: `url` of a loopback stub, `headers` with a made-up `Authorization: Bearer lit-global-marker-5555` and `X-Spike-Via: global`. The user started a fresh agy and sent one prompt with no tools. A stub I started (scratch, not in git, loopback only) logged every request.

| Question | Observed |
| --- | --- |
| Does a literal `Authorization` header on a global-scope http server reach the server? | **Yes.** Four POSTs to `/mcp`, every one with `Authorization: Bearer lit-global-marker-5555` and `X-Spike-Via: global`. |
| What does agy's MCP client send first? | `server/discover` (with `_meta` client capabilities), then `initialize` (client name `antigravity-client`, version `v1.0.0`), then `notifications/roots/list_changed`, the last one repeated about 7 s later. The stub answered each with a JSON-RPC error; agy sent no tool call. |
| Startup behaviour | `cli.log`: `MCP: 1 server(s) still connecting after 30s: a2a-hdr-probe`, no error line (the stub's replies were errors, so the server never became ready). The first reply was not reported delayed. |
| Did agy rewrite the file? | No: the size, mode and hash were unchanged between setup and put-back. |
| Put-back | The exact original was restored from the backup; I checked afterwards: hash equal to the pre-edit baseline, `a2a-hdr-probe` absent, mode 664, size 1625, `config.json` and `hooks.json` hashes equal to their baselines, backup deleted. |
| The file's mode | 0664 (group-readable), holding Jev's key and others. Not changed by the probe; the user is to set 0600. |
| Chezmoi | `chezmoi source-path` says the file is **not managed** (checked 2026-11-23); earlier notes in the plan assumed it was. |

## 3. What this decides (user, 2026-11-23, option C)
